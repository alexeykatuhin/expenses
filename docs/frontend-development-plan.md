# План разработки фронтенд-приложения

План составлен для приложения учета семейных доходов и расходов на основе текущего проекта `front` и API из `docs/family-expenses-crud-api.md`.

## Исходное состояние

Фронтенд сейчас минимальный:

- Vite + Vue 3;
- один корневой компонент `src/App.vue`;
- нет роутинга, стора, API-клиента и компонентной структуры.

Это позволяет развивать приложение без миграции существующей логики.

## Цель MVP

Сделать приложение, где пользователь может:

1. Зарегистрироваться и войти.
2. Добавлять доходы и расходы.
3. Смотреть общую ленту операций.
4. Фильтровать операции по периоду, типу, категории и подкатегории.
5. Редактировать и удалять операции.
6. Управлять категориями и подкатегориями доходов и расходов.
7. Видеть простую сводку: доходы, расходы, баланс.

## Этап 1. Базовая архитектура фронта — выполнено

Добавить структуру:

```text
front/src/
  api/
    http.js
    authApi.js
    operationsApi.js
    incomesApi.js
    expensesApi.js
    categoriesApi.js
    reportsApi.js
  components/
  pages/
  stores/
  router/
  utils/
```

Установить базовые зависимости:

```bash
npm install vue-router pinia
```

Опционально для иконок:

```bash
npm install lucide-vue-next
```

Основные задачи:

- настроить `vue-router`;
- настроить `pinia`;
- сделать общий HTTP-клиент поверх `fetch`;
- хранить `access_token`, `refresh_token` и `user` в auth-store;
- добавить обработку `401` с обновлением токена;
- вынести базовый URL API в `.env`, например `VITE_API_BASE_URL=/api/v1`.

## Этап 2. Авторизация — выполнено

Страницы:

```text
/login
/register
```

Функциональность:

- регистрация через `POST /api/v1/auth/register`;
- вход через `POST /api/v1/auth/login`;
- выход через `POST /api/v1/auth/logout`;
- получение текущего пользователя через `GET /api/v1/users/me`;
- защита приватных роутов;
- редирект неавторизованного пользователя на `/login`.

Нужно сразу заложить обработку стандартного формата ошибок API:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные запроса",
    "details": []
  }
}
```

## Этап 3. Основной layout приложения — выполнено

После входа пользователь попадает на главный экран.

Роуты:

```text
/
/operations
/incomes
/expenses
/categories
/profile
```

Layout:

- верхняя панель с именем пользователя и выходом;
- боковая или верхняя навигация;
- основная рабочая область;
- адаптивная верстка под мобильный экран.

Для приложения учета денег лучше использовать спокойный рабочий интерфейс: таблицы, фильтры, компактные формы и предсказуемую навигацию.

## Этап 4. Справочники категорий — выполнено

Нужно реализовать управление четырьмя сущностями:

- категории доходов: `/income-categories`;
- подкатегории доходов: `/income-subcategories`;
- категории расходов: `/expense-categories`;
- подкатегории расходов: `/expense-subcategories`.

Экран `/categories` можно сделать с табами:

```text
Доходы | Расходы
```

Внутри каждого таба:

- список категорий;
- список подкатегорий выбранной категории;
- создание категории;
- редактирование названия;
- переключение `is_active`;
- удаление или деактивация категории.

При создании дохода или расхода нужно показывать только активные категории и подкатегории.

## Этап 5. Форма операции — выполнено

Сделать общий компонент `OperationForm.vue`, который работает и для доходов, и для расходов.

Поля:

- тип: `income` или `expense`;
- категория;
- подкатегория, зависящая от выбранной категории;
- сумма RUB;
- сумма USD;
- дата операции;
- комментарий.

Поведение:

- при выборе типа грузить соответствующие категории;
- при выборе категории грузить подкатегории;
- дата по умолчанию - сегодня;
- суммы валидировать как `>= 0`;
- перед отправкой форматировать суммы до двух знаков;
- для создания использовать `POST /api/v1/incomes` и `POST /api/v1/expenses`;
- для редактирования использовать `PATCH /api/v1/incomes/{id}` и `PATCH /api/v1/expenses/{id}`.

## Этап 6. Лента операций

Основной экран `/operations`.

API:

```http
GET /api/v1/operations?type=expense&date_from=2026-01-01&date_to=2026-01-31&limit=50&offset=0
```

Функциональность:

- таблица или плотный список операций;
- фильтры по периоду, типу, категории и подкатегории;
- пагинация через `limit` и `offset`;
- кнопка добавления операции;
- редактирование операции;
- удаление операции;
- отображение суммы с плюсом для доходов и минусом для расходов.

Для MVP лучше опираться на `/operations` как общий read-only endpoint, а создание, редактирование и удаление делать через `/incomes` и `/expenses`.

## Этап 7. Отдельные экраны доходов и расходов — выполнено

После MVP можно добавить отдельные страницы:

```text
/incomes
/expenses
```

Они будут похожи на `/operations`, но с фиксированным типом и endpoint'ами:

```http
GET /api/v1/incomes
GET /api/v1/expenses
```

Это удобно, если пользователь хочет работать только с одной стороной бюджета.

## Этап 8. Сводка и отчеты — выполнено

На главном экране `/` сделать dashboard.

API:

```http
GET /api/v1/reports/summary
GET /api/v1/reports/by-category
GET /api/v1/reports/by-subcategory
```

MVP dashboard:

- доходы за период;
- расходы за период;
- баланс;
- топ категорий расходов;
- топ категорий доходов.

Период по умолчанию: текущий месяц.

## Этап 9. UX-состояния

Обязательно заложить:

- loading-состояния;
- empty-состояния;
- ошибки валидации по полям;
- общие ошибки сверху формы;
- подтверждение удаления операции;
- disabled-состояния кнопок во время отправки;
- сохранение выбранного периода и фильтров в query string или store.

## Этап 10. Проверка и качество

Минимальная проверка:

```bash
npm run build
```

Если добавлять тесты:

```bash
npm install -D vitest @vue/test-utils jsdom
```

Что стоит покрыть тестами:

- API-клиент и обработку ошибок;
- auth-store;
- форматирование сумм и дат;
- зависимость подкатегорий от выбранной категории;
- форму операции.

## Рекомендуемый порядок реализации

1. Роутер, Pinia, API-клиент, env-конфиг.
2. Авторизация и приватные роуты.
3. Layout приложения.
4. Справочники категорий и подкатегорий.
5. Создание дохода и расхода.
6. Общая лента операций.
7. Редактирование и удаление операций.
8. Dashboard со сводкой.
9. Полировка UX, адаптивность, обработка ошибок.
10. Сборка и базовые тесты.

Начинать лучше с авторизации и API-клиента, потому что почти все остальные экраны зависят от токена, обработки `401` и единого формата ошибок.
